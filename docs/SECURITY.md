# Security model and release boundary

M0/M1/M2A/M2B.1 are **local development only**, with no internet release configuration. Settings require LAB_LOCAL_DEV=1, an environment secret and loopback Host values. Native launch binds 127.0.0.1; the optional unverified container binds internally but publishes loopback only. No Windows security settings are changed. M2A API/session/token/artifact details and tested limits are in [M2A.md](M2A.md).

## Accounts and sessions

- Invite-only humans; no public registration, default passwords or shared accounts. First platform admin is created with the interactive bootstrap command. Passwords use Django's PBKDF2 hashing and configured validators (12+ characters). Authentication errors do not distinguish inactive/unknown accounts.
- Roles are project-scoped except platform superusers. Project managers can change memberships and grants, not is_staff/is_superuser. They cannot change their own membership through the portal. Adding an existing account to another project is a trusted OS operation via `add_member`; new users use invitations. Platform-wide account deactivation is currently a trusted local ORM/OS administration operation, not a web form.
- Invite codes contain 256 random bits, expire after 24 hours and are stored as SHA-256 hashes. Acceptance consumes the code in the same transaction as account/membership/audit creation. PostgreSQL row locking is present but not verified here. A revoked/inactive/demoted inviter invalidates pending invitations. Existing accounts cannot have their password reset by accepting a new invitation. Invite codes are entered in POST bodies, not URLs.
- Recovery uses Django's expiring, password-bound single-use tokens (30 minutes). Local messages go only to ignored `.local/mail/`, never to an external mailbox or console. The trusted OS operator can read this sink; it is not an internet mail service. Django redirects the token-bearing recovery URL to a token-free form. The development access logger redacts recovery paths. Any future proxy/access/error logger must also redact tokens and omit request bodies.
- Sessions expire 30 minutes after login (not sliding). Logout flushes the current session; password recovery invalidates the authentication hash. Django rejects inactive users on their next request. Membership/role/grant authority is queried per request, not stored in sessions. M2A adds global session_epoch invalidation via platform-admin account API; deactivation/reactivation increments it so old sessions cannot revive. Existing pre-epoch sessions must sign in again. The endpoint denies project admins and service credentials; no global account-edit HTML interface is provided. Deactivation also revokes outstanding invitations and service tokens/disables principals; reactivation does not restore them.
- Login and recovery use SQL-backed fixed 10-minute windows keyed by secret HMACs of account and direct source IP: 5/account and 30/IP. Counts include successful attempts; blocked login responds 429 even for valid passwords. Forwarded IP headers are ignored; this is not configured for proxies. Invitation attempts share a separate conservative limit. This limits local brute force; distributed abuse, bucket retention cleanup and proxy-aware controls remain later deployment work.

## Access and audit

Every scoped view denies missing/inactive membership. Non-managers read granted devices/tests; engineers may read their own drafts. Ungranted published-version records are hidden from other non-manager/non-author users. Foreign/ungranted object pages return 404. Viewer run submission returns 403; legacy execution POST returns 409, while new M2A queue routes accept approved explicitly granted versions/devices/inputs and create no execution. Every batch item is validated before inserts; current approval/grants are checked even on replay. Inputs can be downloaded only by their owner/scoped service or project admin. No execution result/output/cancellation engine or public Django admin is enabled. M2B.1 enables only agent identity enrollment and idle contact.

Managers create grants only between memberships/resources within the current project. Forms allowlist fields and roles. Access mutations and their audit events commit together. Global login/logout/recovery events appear only to platform administrators; project managers see their own project events. Audit rows are append-only to normal users through the application; they are not tamper-proof. The application database account and OS operator are trusted.

Private responses use no-store and same-origin referrer policy (cross-origin referrers suppressed), session cookies are HttpOnly/SameSite=Lax, forms use CSRF and GET cannot mutate memberships/grants/logout. Local cookies intentionally lack Secure because the loopback server is HTTP. **Before any non-local release** require HTTPS, Secure session/CSRF cookies, HSTS, maintained interpreter/dependencies, administrator MFA (prefer maintained OIDC), proxy/host review, mail delivery, database least privilege, real PostgreSQL integration tests, session revocation tooling and log review. No public-hosting workflow is implemented or authorized.

The in-app browser sends Origin:null for form POSTs in this environment; Django rejects it. Do not add null to trusted origins or disable CSRF for a preview. Authentication works in direct same-origin HTTP tests; browser layout snapshots provide visual evidence only.

## Hardware boundary (planned)

Gate numbers and normative future requirements follow [PLAN.md](PLAN.md) and [REQUIREMENTS.md](REQUIREMENTS.md); this reconciliation adds no running services or deployment authorization.

Revocation will block dispatch immediately; running work will request cancellation at safe checkpoints and record pending/confirmed states while retaining requester attribution. Never reuse hardware after a lease expires until prior work is confirmed stopped and readiness passes. Otherwise quarantine the resource as unavailable; quarantine itself is not permission to reuse. No running work exists yet.

Future adapters expose discover/identify/capabilities/prepare/execute/collect/cleanup with allowlisted commands and validated bounded parameters. Serial numbers identify inventory, not authentication. Storage tests touch only owned temporary files inside approved contained directories; reject symlink/reparse escapes. No raw disks, formatting, partitions or arbitrary paths. Network tests target configured local endpoints with bounded traffic. Agents authenticate all calls and access only assigned devices/jobs. No temperature/power/GPU data is fabricated.

CAN comparison initially analyzes synthetic authorized expected/actual files; it does not capture physical CAN or authorize use of employer data. Header-removal policy belongs to the approved immutable test version; callers cannot skip arbitrary bytes to force PASS. Raw/normalized inputs and checksums remain evidence. Plugin additions are trusted installed packages, never remote code downloads.

M2A now provides audited account-wide session invalidation, account/invitation revocation and scoped service-token management. Future agents will use separate revocable/rotatable hashed credentials. API submission checks ownership/schema/capabilities and whole-batch authorization before inserting jobs. Dispatch recheck is still required in M2B/M3. Token endpoints cannot bypass authorization or implicitly fall back to ambient sessions. The first real integration cluster is workspace-owned, SCRAM-authenticated and loopback-only; its DB superuser is local test infrastructure, not an app user/production role. No existing cluster/service is modified.

Agent journal/epoch fencing and stable result checksums prevent duplicate/conflicting delivery from being treated as new work; they do not physically stop an old workload. Quarantined resources remain unavailable. After cancellation/timeout, confirm process-tree termination and readiness before release. Preserve original outcome, cleanup state and incomplete-artifact flags separately. Only configured transient infrastructure retries are eligible, never silent assertion retry into PASS or repeated non-idempotent hardware actions.

M4 physical CI requires protected/manual dedicated tagged runners; untrusted branch jobs receive no personal hardware credentials. The application remains local until explicitly authorized deployment. Trusted-LAN phone testing in M5 requires TLS/correct hosts/cookies, reviewed network/firewall settings and test accounts; no database/agent-management exposure. Complete documented release controls before non-local use, including secure session/CSRF cookies; administrator MFA/OIDC is mandatory before any internet release. This plan changes no firewall/bind/security setting and authorizes no public hosting.

## M2B.1 identity boundary

Agent credentials are separate from session and CI authority. Human project administrators manage identities with CSRF protection; CI principals cannot enroll/manage agents. Single-use enrollment expires after 15 minutes and rechecks its issuer. Runtime credentials expire after seven days; SQL stores hashes only. Rotation, revocation, disablement and scope changes invalidate prior authority immediately. Device identity bindings have an active uniqueness constraint but do not reserve hardware. No contact timeout releases resources.

The native client accepts verified HTTPS or literal loopback HTTP, rejects redirects and URL credentials, disables inherited proxies and bounds transport/files. Secrets travel via headers/private files, never URLs or CLI arguments. Exclusive state writes preserve existing files; Windows inherited ACLs remain the user's storage boundary, with no host ACL changes. TLS initialization errors fail safely; an existing local monitoring hook was preserved. Detailed routes, retention limits, recovery and verified checks are in [M2B_1.md](M2B_1.md). No workload dispatch or execution readiness is implied.

## M2B.2 local comparator

Only explicitly selected local synthetic files are analyzed by the opt-in CLI. A static plugin registry denies unknown code/import/commands; schema/roles/header policy and package identity are checked. Input reads and detailed mismatch lists are bounded. Local output requires a new directory and preserves existing evidence. No backend caller supplies local file paths, no physical CAN capture and no workload dispatch are enabled. The release wheel check compares installed modules and records a real artifact SHA-256, not code signing or a sandbox. Local OS/files are trusted. New package-bound SQL versions require separate approval/grants and cannot upgrade historical queued snapshots. See [M2B_2.md](M2B_2.md).
