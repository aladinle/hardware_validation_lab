# M2B.4 - durable local journal and evidence spool

Implemented locally for review on `codex/m2b.4-durable-agent-journal`. **Main merge requires user approval.** No M2B.4 commit/push/merge is authorized by this checkpoint. This task adds local persistence to the reviewed runner. It does not enable backend dispatch/polling, SQL Attempts/resource reservations, real upload acknowledgements or hardware readiness. Those remain at M2B.5/.6 and later gates. Exact evidence is in [STATUS.md](STATUS.md).

## Problem solved and durable sequence

An agent may crash after accepting work, after creating a child but before recording its PID, or after finishing without returning its result. Repeated delivery must not be interpreted as a new execution. One private journal per agent/runtime stores accepted execution ID, epoch, canonical request hash, immutable manifest/parameters/inputs, supervisor identity, launch intent and worker creation identity. Intent is committed before any process creation; worker identity is committed before opening the plugin launch gate.

Local state sequence:

```text
ACCEPTED -> LAUNCH_INTENT -> STARTING -> RUNNING -> COMPLETE -> ACKNOWLEDGED
                 any ambiguous restart -> UNCERTAIN (no automatic relaunch)
```

RUNNING records permission to open the gate, not proof of physical action. launch_intents is a durable intent count, not an exact count of processes actually created in an unrecorded crash gap. spawn_records counts persisted observations; the native tests separately record observed process creation. A rerun needs a new execution ID; reusing the same ID with a different epoch/body is rejected. Changed list ordering/UUID representation is canonicalized where defined; accepted context is never silently replaced.

New deliveries first validate identity/schema, roles/header policy, bounded actual input sizes/checksums and installed package digest. Only then do they atomically accept and claim overlapping local device IDs. Concurrent delivery uses SQLite BEGIN IMMEDIATE and unique execution/device-owner constraints. Replay returns the existing status/result and never calls the runner again, even when original input files are gone. Local SQLite is solely the agent ledger, not PostgreSQL scheduling authority or a hardware lease. No network endpoint accepts these local-demo packets.

The runner writes into a per-execution private spool. After a confirmed local stop, all retained files are flushed and inventoried by size/SHA-256, then completion.json is exclusively written/flushed before the SQLite completion commit. Recovery can finish that SQL commit if the sealed files, accepted references and retained run.json all agree. A crash before a valid seal remains uncertain even if a PID is absent. Process identity includes PID plus Windows creation FILETIME or Linux boot ID/start ticks; PID reuse never authorizes takeover of old activity. Permission/inspection failures are UNKNOWN, not proof of stopped work. Recovery does not kill arbitrary recorded PIDs or clear uncertain resources on a timer.

If the original supervisor is still alive, recovery returns its existing state. Without a valid completion, a dead/unknown supervisor leaves UNCERTAIN and retains overlapping local ownership. A valid completion releases that local busy scope only when the runner did not require quarantine. Cleanup/termination uncertainty keeps the claim even after acknowledgement. This is a local exclusion/reporting rule; hardware readiness remains NOT_EVALUATED and no backend resource is released.

## Durability, retention and limits

- Explicit new-root initialization; open existing DB with mode=rw. Missing/corrupt databases and unsupported schema/platform fail closed. Never delete/recreate the ledger to make an execution eligible again, run two ledgers for one agent, share it across OS runtimes or restore stale copies to bypass dedup. Initialization does not overwrite existing roots or orphaned evidence.
- SQLite WAL, synchronous=FULL, bounded busy timeout and short write transactions; foreign keys and unique ownership. Schema/application version is checked. File fsync precedes the completion commit. Linux directory fsync is attempted; Python has no portable Windows directory-fsync here. Actual process restarts were tested, not OS power cuts or storage-controller durability.
- Private local filesystem required; no network-share/WAL deployment claim. Root requests mode 0700/files 0600 where supported; Windows inherited ACLs are unchanged. Root/spool paths reject symlinks/reparse traversal. WSL source tests use a separate Linux ledger; do not open the Windows ledger concurrently from Linux.
- Default logical spool budget 256 MiB, configurable 64-1024 MiB at initialization; 1,000 execution tombstones maximum by default. Admission reserves conservative working/output/input capacity; completed entries account for retained bytes. SQLite is bounded to 32,768 pages. These are application admission/file bounds, not an OS-wide disk quota. Unknown activity retains its reservation. A full journal refuses new work instead of evicting evidence or dedup records.
- Source staging is bounded to 1 MiB per role and 20 MiB per wheel, runner controls remain as in M2B.3. Completion inventory is at most 128 regular files; seal at most 64 KiB, retained runner metadata at most 32 KiB. No recursive cleanup/pruning is added.
- Acknowledgement does not prove termination/readiness. Local demo ACK checks the exact execution ID, epoch and completion digest, is idempotent and is explicitly labeled ack_source=local_demo. It keeps the files and dedup tombstone even afterward. Real backend authentication/upload/receipt handling is not implemented. ACK is not a substitute for M2B.6.

## Setup and five-minute test

The clean installed environment `.local/b4-journal-venv` and actual 0.5.0 wheel are retained in this workspace. For a fresh checkout of this feature branch:

```powershell
.\.venv\Scripts\python.exe -m build --no-isolation --sdist-extract-dir .local/build-b4-final --outdir .local/dist-b4-final
.\.venv\Scripts\python.exe -m venv .local/b4-journal-venv
.\.local\b4-journal-venv\Scripts\python.exe -m pip install --no-index --no-deps .local/dist-b4-final/hardware_validation_lab_contracts-0.5.0-py3-none-any.whl
```

Reuse an existing environment deliberately; do not recreate it blindly. CAN algorithm version stays 0.3.0, runner/distribution now 0.5.0 with a new verified wheel digest. Old installed releases/results stay separate and are not upgraded in place. No webserver, PostgreSQL, agent credential or real project/device is needed for the following isolated local demo. The UUIDs below are fictional local scopes, not grants to catalog resources.

1. Minute 0-1: initialize a new journal root and create a candidate local manifest. Choose unused names if these already exist; keep the same root for all replays.

```powershell
$journalRoot = '.local/b4-demo-journal'
.\.local\b4-journal-venv\Scripts\hvl-journal.exe init --root $journalRoot --agent-id 11111111-1111-4111-8111-111111111111 --project-id 22222222-2222-4222-8222-222222222222
.\.local\b4-journal-venv\Scripts\hvl-compare.exe manifest --wheel .local/dist-b4-final/hardware_validation_lab_contracts-0.5.0-py3-none-any.whl --header-bytes 2 --output .local/b4-demo-manifest.json
```

2. Minute 1-2: create one explicit local delivery. make-delivery generates new execution/job/artifact UUIDs, input hashes and a one-hour deadline. Do not regenerate this file when testing replay.

```powershell
.\.local\b4-journal-venv\Scripts\hvl-journal.exe make-delivery --root $journalRoot --manifest .local/b4-demo-manifest.json --device-id 33333333-3333-4333-8333-333333333333 --expected examples/can/expected-header.hex --actual examples/can/actual-pass.hex --output .local/b4-demo-delivery.json
```

3. Minute 2-3: deliver it twice. Each command is a fresh process, so the second demonstrates restart/replay behavior.

```powershell
.\.local\b4-journal-venv\Scripts\hvl-journal.exe deliver --root $journalRoot --assignment .local/b4-demo-delivery.json --expected examples/can/expected-header.hex --actual examples/can/actual-pass.hex --wheel .local/dist-b4-final/hardware_validation_lab_contracts-0.5.0-py3-none-any.whl
$LASTEXITCODE
```

Repeat that exact command. First: newly_accepted=true, state=COMPLETE, result.outcome=PASS, exit 0. Second: newly_accepted=false, same completion_hash/result, launch_intents=1 and spawn_records=1, exit 0. Original data and result are retained under `$journalRoot/spool/EXECUTION_UUID/`. No new native worker is created by replay. To intentionally run again, make a new delivery file/new execution ID while preserving the first.

4. Minute 3-4: inspect and acknowledge locally twice. This simulates a receipt for review, not a real backend upload. It does not remove evidence.

```powershell
$delivery = Get-Content .local/b4-demo-delivery.json -Raw | ConvertFrom-Json
$status = (& .\.local\b4-journal-venv\Scripts\hvl-journal.exe status --root $journalRoot --execution-id $delivery.execution_id) | ConvertFrom-Json
.\.local\b4-journal-venv\Scripts\hvl-journal.exe ack-local --root $journalRoot --execution-id $status.execution_id --epoch $status.epoch --completion-sha256 $status.completion_hash --confirm-local-demo
$LASTEXITCODE
```

Repeat the ACK command: state=ACKNOWLEDGED, ack_source=local_demo, spool_retained=true; exit 0 both times. Changing --epoch to 2 or using a different digest must reject with exit 2 and preserve the existing record. `status` is a metadata read; `recover`, `deliver` replay and ACK validate the completion spool checksums.

5. Minute 4-5: inspect the automated crash matrix, or run it in new disposable test journals:

```powershell
.\.venv\Scripts\python.exe tests/b4_package_smoke.py --python .local/b4-journal-venv/Scripts/python.exe --wheel .local/dist-b4-final/hardware_validation_lab_contracts-0.5.0-py3-none-any.whl
```

Expected lines: repeated delivery -> one observed spawn/stable result; repeated local ACK -> retained spool/stale epoch denied; actual abrupt exits after acceptance, intent, spawn-before-PID-record and gate launch -> UNCERTAIN without relaunch; abrupt exit after valid seal or after completion commit -> COMPLETE without relaunch. The harness deliberately exits only its owned supervisors, never the user webserver or unrelated processes. Separate unit tests prove concurrent delivery, input deletion after completion, record/quota exhaustion, corruption refusal and evidence conflict behavior.

For an uncertain execution, inspect it without rerunning:

```powershell
.\.local\b4-journal-venv\Scripts\hvl-journal.exe recover --root $journalRoot --execution-id EXECUTION_UUID
```

UNCERTAIN is a deliberate safety outcome; this task provides no force-clear/retry switch. Recovery command success (exit 0) means it returned a status, not PASS. Deliver returns 0 for a safely completed PASS, 1 for FAIL, and 2 for ERROR/TIMEOUT/CANCELLED/uncertainty/quarantine. Validation/capacity/conflict failures return 2. Main merge and M2B.5 remain separate user actions.

## Native evidence and limitations

See STATUS for final suite counts/timing and artifact digest. Windows uses a clean Django-free installed wheel/CLI. Existing Ubuntu WSL checks source against the actual matching wheel, not a clean Linux package/service installation. Local SQLite concurrency proves only this local ledger. PostgreSQL's backend permission/idempotency regressions are separately retained in the full suite; backend scheduling is not implemented/proven here.

The known launch/PID-write gap is intentionally not called exactly-once physical execution. A supervisor can die immediately after process creation before identity is persisted; Windows may leave an unassigned suspended child if failure precedes Job Object attachment. The ledger still blocks retries and overlapping local scope. Tests inject a real crash after containment but before PID recording, plus a real post-gate crash; they do not prove every machine instruction, hardware termination or OS power-failure case. No PID absence, supervisor age, heartbeat or ACK releases uncertain resources.

Primary references: [SQLite WAL durability](https://www.sqlite.org/wal.html), [SQLite PRAGMA settings](https://www.sqlite.org/pragma.html), [Windows process identity](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers). Secrets and raw evidence belong only in private ignored runtime storage; the spool is not encrypted/signed against a malicious OS owner.

Three optional exercises: (1) Why must launch intent reach durable storage before process creation, even when PID cannot be recorded atomically? (2) Why does sealed evidence permit completion recovery while a missing PID does not permit rerunning? (3) Why must acknowledgement match epoch/content, and why can it never prove hardware readiness or authorize uncertain resource reuse?
