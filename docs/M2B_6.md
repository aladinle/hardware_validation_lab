# M2B.6 - assignment-bound results and evidence

Implemented locally for review on `codex/m2b.6-results-and-evidence`, based on reviewed M2B.5 merge `b53dd3b`. No commit/push/merge of this task is authorized automatically. Stop before M2B.7; full simulator MVP remains incomplete. Actual results/limits are recorded in [STATUS.md](STATUS.md).

## Problem solved

M2B.5 could finish a native comparison but left the backend with a completion digest and Running/Not evaluated. M2B.6 sends the sealed output inventory, stores immutable SQL outcomes/reports and returns an authenticated completion acknowledgement. A missing upload or lost acknowledgement never becomes a second execution or an invented clean result.

Sequence: claim -> event 1 execution_accepted -> durable journal/contained execution -> local completion receipt -> event 2 local_completion_sealed -> output uploads -> final result commit -> backend ACK -> local ACKNOWLEDGED. The first event records accepted execution context, not proof of physical action. Timestamps are server receipt times and assignment/result creation times; duration is the actual runner observation with seconds as its unit. Unknown physical readiness, firmware and sensors remain unknown. No CI/JUnit or cancellation is added here.

## Contracts and permissions

- Bearer-only agent POST routes: `/api/v1/agents/{agent_id}/events`, `/output`, `/result`. Every call checks current receiver/key/project/device binding and original execution ID/epoch/claim, requester/service authority, approved immutable context, package and lease fencing. No session/CI fallback; browser mutations retain CSRF enforcement.
- Two ordered bounded lifecycle events, unique `(Attempt, sequence)`. Identical replays return the existing record; missing/out-of-order/conflicting events fail. This is coarse progress, not streaming telemetry.
- Output upload uses `application/octet-stream`, a declared bounded length, SHA-256 and fixed logical name. Identity/claim is in headers, never URLs. Allowed names only: run/run.json (32 KiB), run/report.json (8 MiB), run/report.txt (64 KiB), run/stdout.bin (8 MiB), run/stderr.bin (64 KiB). Total maximum 18 MiB per Attempt, five records. JSON must parse strictly; report text must be UTF-8. Names are not filesystem paths; no archive extraction or executable upload.
- Output bytes and checksums are stored together in PostgreSQL bytea. This deliberately avoids a filesystem/object-store write versus SQL commit gap for the bounded prototype. It is not a measured large-scale blob-storage design. Metadata/bytes are immutable; PostgreSQL update/delete triggers protect events, outputs and final results. SQL administrator and agent-host owner remain trusted; hashes are not remote attestation.
- Final result requires the prior matching completion digest, accepted assignment checksum, exact input/package identity, ordered events and every declared run output matching its sealed bytes/checksum. The uploaded runner record must match the seal. Collected CAN JSON is validated against raw accepted inputs, parameters, package and positional semantics; human report must match its JSON. HTTP performs bounded validation only, never workload process execution.
- The stored versioned report includes Attempt/Job/Run/agent/project IDs, epoch, original immutable submission snapshot/assignment, runner outcome, evaluation/cleanup/evidence/termination status, source, timestamps, duration units and downloadable output checksums. Local PASS/FAIL is distinct from platform lifecycle and cleanup. A cleanup failure preserves PASS/FAIL but quarantines resources. INCOMPLETE capture remains explicitly INCOMPLETE even when every retained file has been stored.
- Authorized GET routes: `/api/v1/jobs/{job_id}/result` for the execution envelope and `/api/v1/outputs/{output_id}` for exact bytes. Reads use current job visibility, requester/member/version/device and service-principal scope. A different project/user/service or revoked credential/grant cannot use a copied URL. Files download as attachments/octet-stream with private/no-store/nosniff behavior; content is not served as active HTML.
- Missing result remains Not evaluated with evidence PENDING. A successful result becomes Completed, or Quarantined if cleanup/evidence is unsafe. Minimal job detail exposes outcome, separate statuses and report/download links. Results dashboard, richer progress/cancel controls and full portal integration remain .8.

## Replay, expiry and retained ownership

Identical upload/finalization is idempotent. Different bytes under one name or another completion digest never overwrite the first artifact/outcome. Two actual PostgreSQL upload connections were tested; one immutable output remains. SQL finalization and outcome/ACK eligibility commit together. Agent marks ACKNOWLEDGED only after checking the authenticated response's ID, epoch, completion digest and bound backend origin. Both server and local spool retain evidence; no ACK deletes records/files or releases leases.

For a result already finalized, identical authenticated replay may recover a lost ACK after the original upload deadline/lease expiry. Current permissions, receiver, claim and resource epochs still must match; no new evidence/event/outcome or ownership change is allowed. Before initial finalization, expired/quarantined claims remain rejected. Completed result retention is not changed into lease-expiry failure by the scheduler. A subsequent epoch/resource owner cannot be finalized or released by an old claim.

**All four leases remain held.** Readiness has not yet been established, and there is no release endpoint in this gate. Cleanup/quarantine and single-assignment bounds from .5 remain. Do not clear SQL leases, erase a journal, change historical snapshots or promote an old .6 wheel/job to bypass quarantine. The user's prior M2B.5 execution `08656d14-f297-4972-bf51-fe8c29152acf` stays historical and quarantined; its local PASS is not backfilled as a new M2B.6 result.

## Five-minute success/failure and replay demo

1. Minute 0-1, native shell: `NATIVE_PYTHON -m agent.poller --state-file STATE_PATH --journal-root NEW_ROOT --wheel WHEEL_PATH --init-journal`. Expect no assignment and hardware_ready=false. Later polls omit --init-journal.
2. Within **30 seconds**, backend shell with matching PostgreSQL/secret/flag: `.\.venv\Scripts\python.exe web/manage.py scheduler --confirm-simulated --iterations 1`. Expect one execution ID. Lease deadline is 90 seconds; run the next command immediately.
3. Native shell: `NATIVE_PYTHON -m agent.poller --state-file STATE_PATH --journal-root ROOT --wheel WHEEL_PATH --count 2 --interval 1`. Expect the same ID/epoch on both replies, first newly_accepted=true then false; journal_state=ACKNOWLEDGED, evidence_acknowledged=true, receipt_recorded=true. local_outcome=PASS for actual-pass.hex, FAIL for actual-missing.hex. `leases_released=false`, `hardware_ready=false` throughout. CLI success means protocol delivery succeeded; local FAIL does not make this poller the future M4 CI exit-code CLI.
4. Minute 2-3: refresh job detail. Expect Completed + PASS/FAIL, separate EVALUATED/Cleanup COMPLETE/Evidence COMPLETE, the execution ID and download links. Open the versioned execution JSON, download run/report.json and run/report.txt, compare their recorded SHA-256 to downloaded files with Get-FileHash. For actual-missing.hex, report must show one missing byte; do not replace that failure with PASS.
5. Minute 3-5: repeat polling or restart the native process with the same state/root. It must keep the same execution/result and one spawn. Spool and SQL evidence remain. To test the other outcome, prepare another fresh isolated database/scope; this gate deliberately retains the global allocation, even after success. To test read denial, use an ungranted account or revoke the requester's device grant and retry the report/output URL: deny access, preserve original result. Avoid revoking your only admin account.

An unfinalized expired job remains quarantined and cannot be upgraded into a completed result. A failed/incomplete upload leaves local COMPLETE spool pending, backend evidence pending and held leases. Restore service and retry within the original allocation deadline; if expired, retain evidence for future reconciliation. No delete/reinitialize/manual SQL release workaround.
