# M2B.1 - native agent identity and idle contact

Implemented locally on 2026-11-05. An administrator can enroll a device-scoped agent; the independently installed native Windows process can authenticate and send idle heartbeats. No agent can claim a job, execute a plugin, discover hardware, mark a device ready or upload execution results in this task. M2B.2 onward remains planned. See [M2B.md](M2B.md) for the eight-task sequence and [STATUS.md](STATUS.md) for actual evidence.

## What a heartbeat proves

A credentialed process contacted the backend at the server-recorded timestamp and asserted its approved inventory scope. Reported OS/version are self-reported process metadata, not hardware attestation. Hardware connected/readiness remain unknown/not evaluated; response assignment is null and execution_available is false. Historical last-contact time is not a current liveness guarantee, device ownership lease or proof that a workload stopped. No scheduler/offline detector runs in this task.

Agent authority is separate from humans and CI service principals. Initial enrollment is approved by a project administrator (or platform administrator), bound to 1-20 enabled inventory devices in that project and limited by a single-use 15-minute random enrollment credential. Its issuer must still have active administrator authority when consumed. On enrollment, the backend consumes that credential transactionally and returns a separate seven-day random agent credential. Only SHA-256 digests are stored in SQL. Two PostgreSQL connections racing the same ticket cannot both succeed.

Every heartbeat checks the exact agent identity, enabled/enrolled status, credential expiry/revocation and active enabled same-project device bindings. No cookie, human password, CI credential or another agent's key substitutes for it. Inventory scope changes invalidate old credentials and require reenrollment. One active agent binding per device is constrained in SQL; this is identity assignment, not a hardware-execution reservation or lease. Disabled/revoked agents do not automatically release inventory for reuse. Safe hardware reassignment/termination belongs to later tasks.

## Start the backend and install the native package

Use the existing native PostgreSQL setup from [M2A.md](M2A.md). Run from the workspace in one PowerShell session:

```powershell
.\scripts\postgres-local.ps1 -Action start
.\scripts\postgres-local.ps1 -Action migrate
.\scripts\lab.ps1 -Action run
```

Choose your own human administrator with interactive bootstrap if the PostgreSQL lab database has none. Existing SQLite accounts remain in their separate DB. No default human credentials are supplied. The additive 0004 migration preserves existing inventory/jobs and adds agent tables plus the inventory enabled flag.

The root pyproject now builds a single wheel containing separate Python packages `contracts` and `agent`, version 0.2.0, with the `hvl-agent` command. The native package has no Django dependency. Django remains in the web environment only; this is a separate process, not code running inside a web request worker. No service installation, USB driver, system Python modification or privileged component is needed.

The completed local build and clean environment are retained under ignored `.local/dist-b1-final/` and `.local/b1-agent-venv/`. To reproduce on a new checkout:

```powershell
.\.venv\Scripts\python -m build --no-isolation --sdist-extract-dir .local/build-b1-final --outdir .local/dist-b1-final
python -m venv .local/b1-agent-venv
.\.local\b1-agent-venv\Scripts\python -m pip install --no-index --no-deps .local/dist-b1-final/hardware_validation_lab_contracts-0.2.0-py3-none-any.whl
.\.local\b1-agent-venv\Scripts\hvl-agent.exe --version
```

Do not recreate a pre-existing virtual environment blindly; inspect/reuse your own or choose a new directory. The verified clean environment imported the installed packages from outside the checkout root with Django absent. Only native Windows was exercised; Linux/macOS runtime and service behavior remain unverified. No Mac hardware validation or Apple certification is claimed.

## Enroll and contact

1. In a regular local browser, sign in as project administrator and open **Devices -> Manage agent enrollment & contact**.
2. Create an identity and select permitted existing inventory. Save the downloaded enrollment JSON privately as `.local/agent-enrollment.json` on the intended agent host. If using synthetic inventory, keep it clearly simulated. Selecting metadata does not discover or ready physical hardware.
3. In another PowerShell window, run the native client below. Neither token nor password goes in an argument or URL.

```powershell
.\.local\b1-agent-venv\Scripts\hvl-agent.exe enroll --server http://127.0.0.1:8765 --invitation-file .local/agent-enrollment.json --state-file .local/agent-state.json
.\.local\b1-agent-venv\Scripts\hvl-agent.exe heartbeat --state-file .local/agent-state.json --count 3 --interval 5
```

The default is one heartbeat; count is bounded to 1-1000 and interval to 1-300 seconds. Runs remain foreground and finite, with a five-second HTTP timeout. Ctrl+C returns exit 130. Errors return exit 2 with a fixed safe message, not raw responses, credentials or tracebacks. Output allows only identity/contact/idle status. A state file is credential storage, not the durable execution journal planned for M2B.4.

The state file is created exclusively: existing files are preserved. Files must be bounded regular files without links; state directories reject symlink/reparse paths. New files request mode 0600 on systems supporting it; Windows uses inherited ACLs, which were not changed or represented as a new owner-only ACL. Keep the files in a trusted private ignored directory, out of Git, Docker context, screenshots and logs. The trusted OS operator can read them; this is not encrypted secret storage.

If enrollment was accepted but its response/state write was lost, the one-use ticket stays consumed. An administrator reissues enrollment, which invalidates old enrollment/runtime credentials; retry with the new invitation and a new state path. No automatic retry conceals ambiguous credential delivery.

## Rotation, revocation and scope changes

On the agent-admin page, **Rotate & download agent credential** revokes existing credentials and downloads a new credential. It requires an already enrolled enabled agent with valid device scope. Save it privately, then replace local state using a new output file:

```powershell
.\.local\b1-agent-venv\Scripts\hvl-agent.exe install-credential --state-file .local/agent-state.json --credential-file .local/agent-rotated.json --output-file .local/agent-state-new.json
.\.local\b1-agent-venv\Scripts\hvl-agent.exe heartbeat --state-file .local/agent-state-new.json
```

Replacement permits an expired old file as an identity reference but requires matching agent/project/device scope and an unexpired new credential. It does not authorize a broader scope. Existing output files are preserved. **Revoke credentials** invalidates runtime/pending enrollment keys; **Disable agent** additionally disables the identity. Reenable through administrator-controlled reenrollment, not a local client switch. Revocation of a human creator's login does not turn an enrolled machine into a human session; pending enrollment requires the issuer's current authority, while enrolled machine credentials are managed explicitly. Future dispatch must still check the job requester's current permissions.

The admin API's set_devices action replaces scope within the same project, invalidates old credentials and returns new enrollment. No discovery-based reassignment exists. Reenrollment preserves historical last-contact time until a new heartbeat; it does not mark contact fresh or device ready.

## Versioned routes and contracts

| Route | Authority / behavior |
| --- | --- |
| `/api/v1/projects/PROJECT_UUID/agents` | Human admin session + CSRF. GET bounded list; POST `{name, device_ids}` creates identity and returns enrollment JSON once |
| `/api/v1/projects/PROJECT_UUID/agents/AGENT_UUID` | Human admin + CSRF. POST `{action}` with rotate, reenroll, revoke, disable; set_devices also requires device_ids |
| `/api/v1/agents/AGENT_UUID/enroll` | POST with `Authorization: Enrollment ...`; exact schema/version/platform/device scope; one-use credential |
| `/api/v1/agents/AGENT_UUID/heartbeat` | POST with agent Bearer credential; idle heartbeat only, no browser/CI fallback |
| `/projects/PROJECT_UUID/agents/` | Human project-admin HTML management/download forms; other roles/foreign projects denied |

Every JSON message is bounded to 64 KiB, with strict supported fields, schema version, UUIDs, bounded strings and timezone-aware timestamps. Heartbeat must explicitly send observations=[], active_execution_id=null and ready=false. The server uses received time for contact; sent_at is untrusted reported time. Repeated retained heartbeat ID/body is accepted without refreshing contact; same ID/different content conflicts (409). Only the latest 1000 heartbeat identities per agent are retained, so dedup is bounded to that window. Security audit records are not pruned. This is not the future execution journal/result-replay guarantee.

[agents_v1.py](../contracts/agents_v1.py) also defines typed future Assignment/Cancellation/ProgressEvent/Result/ArtifactDeclaration structures. These definitions are not enabled endpoints or runtime payload validators for those future operations. Claim/cancel/event/result/upload execution routes remain unavailable until their tasks; no code executes a received assignment. Existing M2A job API remains queued-only. Disabled inventory now rejects new job submissions as well as agent contact.

The client [transport](../agent/transport.py) uses a verified default TLS context, permits plaintext HTTP only for explicit loopback origins, disables environment proxy inheritance, rejects redirects and bounds response size/time. It refuses URL credentials/path/query/fragment. No insecure TLS option or inbound public agent port exists. Backend payloads cannot choose local executables or filesystem paths. The local sandbox can deny TLS initialization through an existing environment hook; the client fails safely and no host hook, certificate, verification or security settings are changed. A regular host execution was verified with approved tool access; real HTTPS deployment remains untested.

Primary references checked during implementation: [Python HTTP/redirect/TLS transport](https://docs.python.org/3.11/library/urllib.request.html) and [Django transaction boundaries](https://docs.djangoproject.com/en/5.2/topics/db/transactions/). No production/internet release is configured.

## Validation, limits and five-minute demo

The PostgreSQL suite includes the existing portal/submission regressions plus enrollment, cross-role/project/agent denial, CSRF, expiry/rotation/revocation, disabled/removed scope, request bounds, replay/conflict, SQL scope uniqueness and concurrent one-use enrollment. Real loopback transport tests verify redirect refusal/response bounds and safe errors. Live HTTP plus a separately installed clean Windows agent process proved actual enrollment, repeated idle contact, rotation and revocation, with secret-free captured output. Static checks, migration consistency and source/wheel packaging passed; exact counts/times are recorded in STATUS.

Human admin-page layout was checked through labeled actual-template snapshots at desktop and phone widths, with inactive forms and no credential values. This does not prove browser sign-in or physical-phone access. The in-app browser's Origin:null limitation remains; same-origin HTTP login was verified. No hardware integration, scheduler, plugin, execution journal/spool, results, Docker/hosted CI/Linux agent or current-device readiness is claimed. JSON credential file storage trusts the local OS; lost responses need explicit administrator reissue.

Five-minute demo:

1. Minute 0-1: start PostgreSQL/web, open the admin agent page and identify a synthetic offline inventory scope.
2. Minute 1-2: create identity/download enrollment, then run the installed native client using file paths. Explain why the one-use credential differs from the runtime credential.
3. Minute 2-3: send two heartbeats and inspect the server timestamp/reported OS. Show assignment=null, readiness false and no jobs executed.
4. Minute 3-4: rotate/download, show old-state contact fails, install into a new state file and show new-state contact succeeds. Revoke and show exit 2.
5. Minute 4-5: point to PostgreSQL's concurrent enrollment check and wrong-agent/device/role tests; explain what awaits M2B.2 and M2B.5.

Three optional exercises: (1) Why separate one-use enrollment, agent and CI credentials? (2) Why does a successful heartbeat not prove that a device is ready or a workload stopped? (3) Why should a redirect or ambiguous enrollment response fail safely instead of silently retrying with the credential?
