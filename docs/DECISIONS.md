# Decisions

1. **Django 5.2.18 LTS + Python 3.11.** Official [download/support table](https://www.djangoproject.com/download/) and [5.2 release notes](https://docs.djangoproject.com/en/5.2/releases/5.2/) checked on 2026-11-02. 5.2 supports Python 3.11 and has an LTS support window through April 2028. PyPI confirmed 5.2.18 available; installed version was checked. Latest overall Django would require a newer Python. requirements.lock pins the resolved runtime; source requirements show intentional top-level dependencies.
2. **Server templates before a SPA.** Ordinary forms and shared authorization querysets are easier to inspect in a two-hour daily learning window. No measured need for an SPA exists.
3. **Custom user from the first migration.** Keep Django's hashing, sessions and authentication while making account email unique. Bootstrap/invitation normalize emails. Local OS operators must preserve that normalization. Later OIDC can link external identity without replacing project memberships.
4. **SQLite only for explicit quick start.** Docker CLI exists, engine stopped; psql absent. PostgreSQL config/Compose/non-container steps are supplied but unverified. No PostgreSQL concurrency claim is made. The major PostgreSQL image tag is intentionally updateable; digest pinning waits for an actual integration run.
5. **Scope models to implemented features.** Catalog Device/TestDefinition and grants exist; approved immutable versions/jobs/leases/results are deferred to their gates. An inventory record is never called connected. Role actions to run are disabled or denied server-side.
6. **No role-preview switch in M1.** Distinct accounts and direct HTTP tests demonstrate role behavior without altering an admin's identity or quietly impersonating a role.
7. **Local review data is isolated.** Browser review uses a separate ignored SQLite file and temporary random credentials, never default/shared application credentials. Rendered snapshots are labeled and contain no executable forms. The in-app browser's null Origin rejection is preserved; it is not counted as a successful interactive login.
8. **Windows native agent later.** Backend/workers target Linux/WSL2, but Windows-attached hardware may require a native Windows Python agent. WSL USB access is not assumed. No hardware claim is made today.
9. **TLS remained verified during setup.** Bundled pip 23 could not use the Windows trust store. pip 26.3 was downloaded via Windows HTTPS and SHA-256 checked against PyPI metadata, then installed into .venv; dependency installation used normal TLS verification. No host certificate/security settings were changed.

## Reconciliation decisions - 2026-11-03

10. **One project, one roadmap.** The user requested merging the original brief and LabFlow PDF, not implementing the PDF prompt or renaming the app. Hardware Validation Lab remains the product; PLAN is canonical, REQUIREMENTS maps coverage, STATUS records evidence. Historical M0/M1 reports remain unchanged evidence. Future milestone names follow PLAN's explicit crosswalk.
11. **Preserve Django and transfer backend behaviors.** Keep the original approved/implemented Django ORM/migrations/auth/templates instead of FastAPI/SQLAlchemy/Alembic/Jinja. Typed JSON schemas, durable SQL jobs, agent APIs, plugin extensibility and CI remain required. HTMX is optional, minimal polling sufficient. Do not claim FastAPI-specific experience from Django implementation or rewrite existing Django tests to pytest merely for tool-name parity.
12. **Bridge the actual gap before execution.** M2 is split into reviewed M2A (real PostgreSQL, immutable approved catalog, input artifacts, service identities, idempotent durable queued jobs/API) and M2B (native local agent/simulator/bounded execution/reports). PDF Milestone 1 is not retrospectively claimed complete by the existing portal. PostgreSQL availability is a real M2A prerequisite; blocked integration cannot be passed on SQLite.
13. **CAN comparison first, no physical CAN claim.** Synthetic file fixtures model the user's comparison workflow. Approved header policy, explicit expected/actual inputs, normalized offsets and length/positional evidence prevent misleading PASS/mismatch claims. Physical capture requires a separately tested owned adapter. No confidential employer data is imported by this plan.
14. **Identity and outcome vocabulary.** Attempt ID is PDF execution_id; Job/Run/Attempt stay distinct. Repeated delivery reuses ID, actual reruns get a new attempt and lineage. Keep reserved/PASS/FAIL/ERROR/TIMEOUT/CANCELLED; map PDF ASSIGNED to reserved and NOT_EVALUATED to evaluation_status. Product assertion deadline may be FAIL; runner deadline is infrastructure TIMEOUT. Cleanup/readiness/evidence completeness remain independent. CLI/JUnit map these explicitly.
15. **Proof order before extra services.** Prove core scheduler/recovery (M3), core CI/reporting (M4), then physical/Unix (M5). Coordinated reservations are a separate M3C review. Retain all original portfolio technologies: Celery/RabbitMQ M6A, InfluxDB/MongoDB/C++ M6B, Kafka/Kubernetes/Snowflake M7. They are planned requirements, not simulator-MVP dependencies or current skills. Hardware absence can permit later simulation-only continuation only after explicit sign-off, without claiming physical completion.
16. **Outbox at first broker, not only Kafka.** SQL/publication atomicity becomes relevant when RabbitMQ arrives in M6A; implement reliable outbox publication/dedup then, extend to Kafka later. PostgreSQL stays authoritative; generic workers/cluster processes never inherit unowned hardware access.
17. **Environment and learning claims stay honest.** Physical-phone networking, actual Linux/Windows service behavior, hosted CI, hardware and Snowflake require real access/evidence. PDF timing targets/90-130-hour core estimate are proposed, unmeasured and do not cover the expanded stack. Re-estimate gates as inspected; no unattended work/remote/push/install/spending authorization is inferred.

## M2A implementation decisions - 2026-11-03

18. **Use installed PostgreSQL without privileged setup.** Despite psql not being on PATH, PostgreSQL 18.1 binaries exist under Program Files. A separate `.local/m2a-pg` cluster with generated SCRAM password on 127.0.0.1:55439 established real integration evidence. No Windows service/other cluster/security setting was modified; Docker stays unavailable. Compose/CI target PostgreSQL 16 remains unverified. Existing SQLite accounts/data are not silently migrated.
19. **Metadata approval is not execution.** Draft header policy is mutable; published version+manifest digest are immutable. Executable package digest stays null and execution_available false until M2B builds a real package. Version-specific grant plus device grant is required even for platform-admin submission. The seed is explicit opt-in simulated offline metadata and creates no results. Input comparison remains unimplemented.
20. **Idempotency has an accountable principal.** Lock current requester User then Project, validate all items, freeze request/snapshot and rely on requester-scoped unique key+canonical hash. Human and service keys are separate. Same request returns existing IDs; changed body conflicts; unauthorized item creates no jobs. Real competing PostgreSQL connections verified this, not device reservation correctness.
21. **Immutable SQL input/version metadata; private file limitations.** PostgreSQL triggers protect version/input rows including queryset changes; SQLite update-only triggers support test flush. Private generated blobs are size/path/checksum guarded and exact duplicate uploads reuse metadata. A process crash before SQL commit may leave unreferenced private blobs; no automatic destructive orphan cleanup or tamper-proof claim. Input/output artifact capabilities remain separate (outputs later).
22. **Global session epochs and explicit bearer authority.** Session revoke/deactivate/reactivate rotates the account epoch, preventing old-session revival; migration requires old sessions to reauthenticate. Account endpoints are platform-admin only and defer platform-admin target changes to a reviewed local procedure. Service scopes also require current owner membership/grants and never fall back to cookies on invalid token. No credentials are printed/committed; temporary QA credentials are retired.
23. **Packaging and CI evidence scope.** Official PyPI metadata and local installation resolved pinned build 1.6.1, ruff 0.17.3, setuptools 84.2.1 and wheel 0.48.0 (Python 3.11 compatible), plus transitive dependencies in the single lock. Source/wheel build passed using a workspace extraction directory after sandbox temp rename failure. CI requires masked secret variables supplied externally; configuration/static/package/Windows-PG18.1 local checks do not prove GitLab/Linux/Docker/PG16 execution. Native PostgreSQL operations require executor network permission in this sandbox; a denied un-escalated probe was repeated successfully with authorized local access.

## M2B.1 decisions - 2026-11-05

- Implement only identity and idle contact before plugins or dispatch. Agent identity bindings remain distinct from execution leases; timestamps cannot establish stopped hardware or readiness.
- Separate single-use enrollment from expiring runtime credentials. Hash SQL secrets, check scope on each request and require reenrollment after scope changes. Retain the latest 1,000 heartbeat IDs; exact retained replay does not refresh contact time.
- Ship one installable contracts/native-agent distribution without Django dependencies. Keep verified TLS, loopback-only HTTP, redirect rejection and file-based secret input. Preserve host monitoring settings. A credential state file is not a durable execution journal.
- Actual Windows native HTTP flow and PostgreSQL integration establish this task's local evidence. Linux/macOS, services, Docker, hosted CI, physical phone/hardware and later execution checks remain open. Stop before M2B.2.

## M2B.2 decisions - 2026-11-05

- Strict byte-pair grammar with contiguous pairs or ASCII space/tab/CR/LF; remove only the declared expected-reference header. Reject empty normalized payloads. Compare positionally, not by edit alignment; report overlap substitutions and tail missing/extra separately.
- Retain bounded raw hex/checksum and normalized evidence, deterministic versioned reports and first 100 details with full totals. ERROR/NOT_EVALUATED is distinct from evaluated product FAIL. These are synthetic local reports, not SQL attempt/hardware outcomes.
- Verify the actual wheel against installed modules before comparing/publishing; bind new immutable versions to its SHA-256. Existing metadata-only publications and queued snapshots remain unchanged; new approval/grants are required. No automatic activation or scheduler execution.
- Keep a local explicit CLI for review and a Django-free clean install. The native agent remains identity/idle only. Runner supervision, journal, dispatch, backend delivery, second plugins and JUnit stay at their gates. User authorized this feature branch and merge to main after checks, not M2B.3.

## M2B.3 decisions - 2026-11-05

- Keep standalone supervision separate from SQL assignment/journaling. Resolve only the fixed installed worker; staged expected/actual roles and verified wheel are local files, never commands or remotely selected executables.
- On Windows launch suspended, attach a Job Object and resume before the plugin gate. Use native aggregate controls and explicit active-process accounting. Preserve host monitoring/temp behavior. Linux uses documented per-process resource limits/groups and records weaker monitoring scopes instead of implying cgroup isolation.
- Keep primary outcome separate from cleanup/evidence/termination. Preserve evaluated PASS/FAIL if cleanup fails, but return exit 2 and require reconciliation. Timeout/cancel and OS-limit infrastructure errors do not become assertion FAIL. Unknown termination never authorizes reuse or physical readiness.
- Build distribution 0.4.0 with unchanged CAN algorithm version 0.3.0 and new artifact digest. Keep old installed releases separate. User requested work on a new branch and explicit approval before main merge; no automatic merge or M2B.4 continuation.

## M2B.4 decisions - 2026-11-05

- Local SQLite WAL/FULL is the agent journal only; PostgreSQL remains platform authority. Persist execution ID/epoch/canonical context, local scope, supervisor and launch intent before creation; record child creation identity before permitting plugin work. Replays never execute again, even after original source files vanish.
- Seal and flush retained evidence before committing SQL completion. Recover a verified sealed completion after the SQL gap; otherwise retain uncertainty/local scope. A missing/reused PID, age, timeout or ACK cannot establish stopped descendants/hardware readiness. Do not introduce an unsafe force-clear switch.
- Bound records and logical spool admission; retain tombstones/evidence even after repeated manual local ACK. Reject capacity exhaustion, corruption, stale epochs and conflicting bytes instead of replacing history. Backend upload/receipt authentication and dispatch stay at their gates.
- Native Windows clean-install and Ubuntu source crash/replay checks are distinct evidence. No exactly-once physical action, OS power-cut/directory durability, malicious OS protection or hosted CI claim. User authorized M2B.4 work on a new branch; main merge still needs approval.
