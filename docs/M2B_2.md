# M2B.2 - synthetic CAN payload file comparison

Implemented locally on 2026-11-05, on feature/m2b.2_synthetic-CAN-file-comparison. This is explicit local file analysis: no physical CAN capture, device discovery/readiness, agent workload dispatch, runner supervision, SQL attempt/result ingestion or hardware result. M2B.3 remains a separate continuation. Actual checks and the authorized merge are reported in [STATUS.md](STATUS.md) and the Git handoff.

## Comparison rules and evidence

Inputs have explicit expected/actual roles. Accept ASCII hex byte pairs, contiguous or separated by ASCII space/tab/CR/LF, case insensitive. Reject odd nibbles, whitespace inside a pair, 0x prefixes, punctuation, comments, BOM, non-ASCII and other control characters. Each raw input is at most 1 MiB. Empty normalized payloads are ERROR, never PASS. The declared 0-4096-byte reference header is removed from decoded **expected only**; actual is already payload. A header consuming/exceeding the reference also yields ERROR. Registry execution must use the exact header size in the supplied immutable manifest; a caller override is rejected before comparison.

Compare normalized bytes positionally, without sequence alignment/edit distance. Count substitutions across the overlap separately from missing/extra tail bytes. A leading insertion can change every overlapping position and add one extra byte. Offsets start at zero in normalized payload space, not hex-text character positions or original reference-file positions.

Reports use schema_version=1, plugin_version=0.3.0, source=simulated, comparison=positional and explicit offset_basis. PASS/FAIL have evaluation_status=EVALUATED; invalid/empty data yield ERROR/NOT_EVALUATED with fixed per-role codes. Reports retain exact raw bytes as raw_content_hex, raw sizes/SHA-256, decoded sizes, removed-header counts, normalized payload hex/checksums, all summary counts and the first 100 differences. Truncation is explicit and does not truncate totals. JSON serialization sorts keys with no timestamps/random IDs; identical inputs/policy/artifact produce byte-identical reports. Human text prints payload offsets, byte values and counts. No JUnit/backend history integration is implemented yet.

## Trusted installed registry and package identity

[contracts/plugins.py](../contracts/plugins.py) defines the allowlisted manifest/schema/capability/role contracts; [workloads/registry.py](../workloads/registry.py) resolves only the installed CAN implementation. No user-controlled import, command or executable is loaded. The existing M2A submission parser now delegates parameter validation to the registry contract, preserving request fields and header semantics. Current object permissions, approval, grants, capability checks, checksum verification and idempotency remain in force.

The 0.3.0 wheel contains contracts, agent and workloads; no new runtime dependency is added. The native agent identity protocol remains unchanged. A local wheel is bounded to 20 MiB; its SHA-256 identifies the actual built artifact. The verifier compares every shipped Python module in those packages with the current installation and checks distribution metadata. Changed modules, unknown modules, duplicate members, wrong metadata or a different approved artifact digest are rejected. This is a trusted local release check, not code signing, supply-chain isolation or remote attestation. Future dispatch must independently verify the approved package and current requester permissions.

Historical M2A versions keep null package digest/execution_available=false. Existing web/API publish actions continue producing metadata-only versions. The trusted local publish_can_workload command creates a **new** package-bound immutable version. Its execution_available=true means a comparator implementation exists, not that platform dispatch is enabled. Separate administrator approval and explicit version grants are required; publication does not grant them, alter old versions/jobs or create an attempt. New jobs remain queued.

## Local installation and five-minute demo

Run from the project root in PowerShell. Existing .local/b2-plugin-venv and the final wheel are retained on this workspace; do not recreate an existing environment blindly. To reproduce elsewhere, build and create a new environment first:

```powershell
.\.venv\Scripts\python.exe -m build --no-isolation --sdist-extract-dir .local/build-b2-release --outdir .local/dist-b2-release
.\.venv\Scripts\python.exe -m venv .local/b2-plugin-venv
.\.local\b2-plugin-venv\Scripts\python.exe -m pip install --no-index --no-deps .local/dist-b2-release/hardware_validation_lab_contracts-0.3.0-py3-none-any.whl
```

Use fresh output paths below; existing files/directories are preserved. The wheel must match the installed code. No web server, agent credentials or database are needed for this local demo.

1. Minute 0-1: create a candidate local manifest with a two-byte expected header. This is not SQL approval or permission to dispatch. The local CLI trusts the operator-selected manifest; it does not authenticate an administrator or fetch approvals.

```powershell
.\.local\b2-plugin-venv\Scripts\hvl-compare.exe manifest --wheel .local/dist-b2-release/hardware_validation_lab_contracts-0.3.0-py3-none-any.whl --header-bytes 2 --output .local/can-demo-manifest.json
```

2. Minute 1-2: compare matching synthetic data. Expect PASS, exit 0, and report.json/report.txt in the new output directory.

```powershell
.\.local\b2-plugin-venv\Scripts\hvl-compare.exe compare --manifest .local/can-demo-manifest.json --wheel .local/dist-b2-release/hardware_validation_lab_contracts-0.3.0-py3-none-any.whl --expected examples/can/expected-header.hex --actual examples/can/actual-pass.hex --header-bytes 2 --output-dir .local/can-demo-pass
$LASTEXITCODE
```

3. Minute 2-3: repeat with --actual examples/can/actual-mismatch.hex and --output-dir .local/can-demo-fail. Expect FAIL/exit 1, one overlapping mismatch at payload offset 2, expected AA/actual AB. Inspect both report files.
4. Minute 3-4: try actual-leading-insertion.hex in a fresh output directory. Expect FAIL, four overlapping mismatches plus one extra byte. Try actual-invalid.hex or actual-empty.hex; expect ERROR/exit 2 and no evaluated assertion.
5. Minute 4-5: keep the two-byte manifest but supply --header-bytes 0 with another fresh output directory. Expect setup rejection/exit 2 and no report directory. Repeat an existing output directory to confirm existing evidence is preserved. An ERROR does not become a product assertion FAIL.

CLI exit mapping applies only to this local analysis tool: 0 PASS, 1 comparison FAIL, 2 invalid/setup ERROR. It is not the future provider-independent M4 job client. Reads are bounded and outputs use a new operator-selected directory, but subprocess supervision/cancel/resource controls belong to M2B.3. Local OS/file access is trusted; no remote-supplied paths are accepted by the backend.

## Publish a new immutable package-bound version

Optional trusted local operation in an already PostgreSQL-configured shell. Copy the draft UUID from Test authoring. Keep header policy in the draft, then run:

```powershell
.\.venv\Scripts\python.exe web/manage.py publish_can_workload PROJECT_UUID DRAFT_UUID AUTHOR_EMAIL --wheel .local/dist-b2-release/hardware_validation_lab_contracts-0.3.0-py3-none-any.whl
```

Authorized authors are project administrators or engineers owning the draft; service principals/viewers/operators cannot publish. Then review/approve that new version and grant it explicitly through the existing portal. A previously approved version/grant never automatically transfers. This step was verified on dedicated PostgreSQL test records, not performed against the user's live catalog.

## Verified evidence and limits

See STATUS for final suite counts/time and actual wheel digest. The suite covers grammar, normalization, bounds, deterministic evidence, positional counts, registry/header/package denial, new publication/approval/grants and preserved old queued snapshots. Package smoke runs seven real fixtures in a separate Django-free installed Windows environment from outside checkout imports. It also checks matching real wheel identity, report replay, output preservation and forbidden header override. These tests are file analysis, not physical CAN validation. No browser flow changes were made; the user's running server/database are left under their control. Linux/macOS, Docker and hosted CI remain unverified.

Three optional exercises: (1) Why does prepending one byte cause multiple positional mismatches? (2) Why must the approved header size stay fixed instead of allowing a caller to skip until data matches? (3) Why does publishing a new wheel-bound version require new approval/grants while preserving old metadata-only queued jobs?
